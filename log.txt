Bạn hãy phân tích repository VietLegal AI hiện tại:
https://github.com/minhvuongle2004/vietlegalAI

Context:
- Đây là một Vietnamese Legal QA/RAG chatbot.
- Hệ thống hiện đã có:
  - FastAPI backend
  - Frontend
  - PostgreSQL/Supabase
  - Qdrant
  - Dense retrieval + Sparse retrieval + RRF
  - BGE-M3 embedding
  - BGE-Reranker-v2-m3
  - CUDA/FP16 reranking
  - deterministic target clause extraction
  - legal version/effective-date awareness
  - multi-intent decomposition
  - benchmark/evaluation pipeline
  - Gemini/OpenAI LLM API
- Mục tiêu dài hạn: mở rộng corpus từ vài chục lên vài trăm văn bản pháp luật để có khả năng giải đáp phần lớn các câu hỏi pháp lý phổ biến của người dân.
- Hiện tại ưu tiên không phải mở rộng corpus tiếp mà là productionize + deploy public + thu thập feedback từ người dùng thật.

MỤC TIÊU:

Thiết kế kế hoạch Production Deployment cho VietLegal AI với các yêu cầu:

1. Public deployment
- Người dùng có thể truy cập chatbot qua Internet.
- Backend/API phải có thể phục vụ nhiều user đồng thời ở mức MVP/public beta.
- Có logging, error handling, health check, monitoring cơ bản.
- Không sử dụng Google Colab làm production server.

2. GPU strategy
- Tôi muốn tận dụng GPU cho BGE-Reranker-v2-m3 vì benchmark hiện tại cho thấy GPU giảm latency reranker rất mạnh.
- Tuy nhiên tôi không có ngân sách để thuê GPU server chạy 24/7.
- Vì vậy hãy ưu tiên kiến trúc:
    CPU backend + GPU inference serverless/on-demand
  thay vì bắt buộc phải thuê dedicated GPU 24/7.
- GPU phải là optional:
    nếu GPU service khả dụng → dùng GPU reranker
    nếu GPU unavailable → fallback sang CPU reranker.
- Không được thiết kế architecture khiến toàn bộ hệ thống phụ thuộc cứng vào GPU.

3. Cost
- Ưu tiên free tier / very-low-cost cho giai đoạn public beta.
- So sánh các lựa chọn phù hợp cho:
    frontend
    backend/FastAPI
    GPU inference
    Qdrant
    PostgreSQL/Supabase
- Cần phân biệt:
    free tier/demo
    low-cost public beta
    production scale
- Không cần tối ưu chi phí tuyệt đối bằng mọi giá; ưu tiên architecture đúng và có khả năng scale.

4. Containerization
- Xác định những thành phần nào nên Dockerize.
- Thiết kế docker-compose cho local development.
- Xác định image/service boundaries.
- GPU inference service phải có khả năng chạy độc lập với backend.
- Backend không nên phải load GPU model trực tiếp nếu architecture serverless GPU được lựa chọn.

5. Recommended architecture
Hãy đề xuất architecture cụ thể tương tự:

Frontend
   ↓
FastAPI Backend
   ↓
Retrieval Layer
   ├── Supabase/PostgreSQL
   └── Qdrant
   ↓
Reranker Service
   ├── GPU serverless/on-demand
   └── CPU fallback
   ↓
LLM API
   ↓
Answer + citations

Nhưng không được mặc định architecture này là đúng tuyệt đối.
Hãy kiểm tra repo hiện tại trước và điều chỉnh theo code thực tế.

7. Legal chatbot specific requirements
Không được làm mất các đặc điểm quan trọng hiện có:
- legal document version awareness
- effective_date / expiry_date
- citation
- article-level evidence
- target clause extraction
- retrieval/reranking pipeline
- source traceability

Khi deploy production, cần đảm bảo:
- Không trả lời dựa trên văn bản đã hết hiệu lực nếu query yêu cầu current law.
- Citation phải truy ngược được tới document/article/chunk.
- Có disclaimer rằng chatbot không thay thế tư vấn pháp lý chính thức.

8. Scalability
Thiết kế architecture có thể tăng từ:
~20–50 users/day
→ 100 users/day
→ 500+ users/day
→ vài trăm legal documents

Mô tả bottleneck có thể xuất hiện ở:
- retrieval
- reranker
- GPU inference queue
- LLM API
- database
- Qdrant
- network
